### R2-02 · 9:26 那一拍的**跨源核验结构上永不触发**，`rejection_disagree` 是死代码

- **文件**：`Backend/neckline/auction/quality.py:433`（`_is_cross_verified`）、
  `:145`（`_FATAL_ERRORS`）、`:298`（`ERR_OPEN_PRICE_MISSING`）、`:541`（唯一调用点）；
  连带 `Backend/neckline/auction/collect.py:183`、`Backend/neckline/api/notify.py:249`
- **事实**（反例 CE-4 实测输出，见 §二）：

  ```
  两源同码同日、一源报 9.0 一源报 11.0、放弃线 9.5（结论明确相反），
  open=0（9:26 的正常状态）→ cross_verified=False  conflict=None  freshness=degraded
  同一组读数，唯一区别是 open>0        → cross_verified=True   conflict=rejection_disagree
  ```

- **根因**：`_is_cross_verified` 的判据是 `len(checks) == 2 and all(c.ok for c in checks)`，
  而 `QuoteCheck.ok` 要求**七项全过**。9:26 时源还没发开盘价 → `ERR_OPEN_PRICE_MISSING`
  → `status = required_field_missing` → `ok == False`。
  可**同一个模块把 `ERR_OPEN_PRICE_MISSING` 明确排除在 `_FATAL_ERRORS` 之外**
  （`:146`），`auction/__init__.py::QF_DEGRADED` 那段更逐字写着
  「开盘价在 9:26 那一拍本来就还没有，把它算致命等于因为一个当时用不上的字段把好端端的竞价价一起扔掉」。
  两处判据不一致 → 非致命项照样把「有没有对拍过」打成 False。
- **为什么是问题**（三层后果）：
  1. **V2.5.0 新造的 `CONFLICT_REJECTION_DISAGREE` 在它专为之而生的那一拍里是死代码**。
     S8 把 K8 的两类冲突合并成它、并把 `rejection_of` 三态钩子从 `pipeline.py:157`
     一路穿到 `collect.py` 再到 `resolve_dual` —— 整条新接线在生产的 9:26 永远走不到。
  2. **`dataQuality` 在 9:26 结构性恒为 `degraded`**（CE-4b 实测：两源全新鲜、无冲突、
     窗内抓完，仍是 `degraded`），因为 `Snapshot.quality_of` 要求 `all_fresh`。
     `ok / degraded / insufficient` 这个三态在核对表上从此不再有分辨力。
  3. **每天早晨的 APNs 都会带一句「（本次数据质量：degraded）」**
     （`notify.py:248-249` 的条件是 `quality != "ok"`）—— 一个天天出现的警告等于没有警告。
- **复现**：见 §二 CE-4 / CE-4b（可直接跑）。
- **修复方向**：把 `_is_cross_verified` 的判据从 `c.ok`（七项全过）改成 `c.usable`
  （无致命项），与 `_FATAL_ERRORS` 的既有语义对齐；`quality_of` / `domain_quality`
  的 `all_fresh` 同理改成「无致命项」，或显式把「9:26 缺开盘价」这一档从 `degraded`
  的成因里摘出去。⚠ 这一改会让 `cross_verified` 的含义变宽，**必须同时补 R2-01 的测试**。
  ⚠ **待确认**：本条完全建立在「9:26 时新浪/腾讯的今开为 0」这个前提上 ——
  该前提是**代码自己两处写死的判断**（`auction/__init__.py` 的 `QF_DEGRADED` 说明
  + `test_auction_checklist.py` 全部 9:26 夹具的 `open_=0.0` 默认值），但仓内没有一条
  实盘证据。建议上产第一周直接记一天 9:26 的 `open` 分布再定改法。

### R2-04 · 策略层**半途失败**会渲染成「今天没有」—— 可被信任的空清单被击穿

- **文件**：`Backend/neckline/report/pipeline.py:127`（`gaps.extend(upstream_gaps)` 只在
  `run is None` 分支里）、`:135`（`params_ok=run is not None`）；
  `Backend/neckline/k9/run.py:346-355`（`save_run` → `save_channel_hits` → `save_listing` 三步顺序）
- **事实**（反例 CE-6 实测输出）：

  ```
  k9_runs 有行（seated_count=2）、k9_listing_entries 零行
  → state: empty | headline: 今天没有 | gaps: ()  ← 缺口一条都没有
  ```

  `_run_k9` 的写入顺序是 `save_run`（先落运行账）→ `save_channel_hits` → `save_listing`。
  中间任何一步抛异常，`report/evening.py::_fuse` 的保险丝把它吞成 `STATUS_FAILED`、
  `_upstream_gaps` 会追加「策略层当日执行失败（见服务端日志）」，
  **但 `build_report` 只在 `run is None` 时才采纳 `upstream_gaps`** —— 运行账已经写进去了，
  于是那条缺口被整条丢掉，`listing_size` 算出 0，三态判成 `EMPTY`。
- **为什么是问题**：架构 §3.5 原文「三种状态在报告首行即可分辨，**空清单可以被信任**」；
  裁定 5 又逐字区分「今天没有＝跑通了、结果为空、可以被信任」与「今天没跑成＝系统没工作」。
  这条路径正好产出**一句每天准时到达手机的谎话**，而且是最难发现的一种：
  首行看不出、gaps 是空的、推送走 `_PUSH_STATE["empty"]` 的**正常文案**
  （`scripts/evening.py:_PUSH_STATE`）。⚠ 库里其实存着自相矛盾的证据 ——
  `k9_runs.seated_count=2` 与清单 0 行 —— 报告没有去比对它。
- **复现**：见 §二 CE-6。
- **修复方向**：
  1. `build_report` 无论 `run` 在不在，都要采纳 `upstream_gaps` 里的**失败**类缺口
     （现在只有 `run is None` 才采纳，那句「报告不猜别人的失败原因」并不要求丢掉别人**说了**的原因）；
  2. 加一条一致性判据：`run["seated_count"] > 0 且 len(listing) == 0` → `NOT_RUN`
     并列出「运行账说 N 只、清单表零行」这条缺口；
  3. 更稳的做法：`_run_k9` 的三步落库放进**同一个事务**，或把 `save_run` 挪到最后
     （运行账代表「这次真的跑完了」）。

## 三、🟡 重要

### R2-05 · 「最多 `maxBackfillRounds` 轮补位」实际是「最多 N−1 次补位」

- **文件**：`Backend/neckline/report/evening.py:282-296`
- **事实**（CE-7）：`rounds_used += 1` 之后立刻 `if rounds_used >= max_rounds: break`，
  而**补位发生在这个 break 之后**。`max_rounds=1` → 剔除 1 只、补位 **0** 只，
  审计链却写「补位轮数已达上限 1，本日清单如实少这几只」。
- **为什么是问题**：§5.5 逐字是「每剔除一只，从 reserve 取下一名再跑解释层 →
  最多 `params.explain.maxBackfillRounds` 轮」。`maxBackfillRounds` 是**参数包里的待配置项**
  （`config/k9-params.example.json:114` 是 `"__TO_BE_CALIBRATED__"`），
  用户按字面意思填 1 会得到「补位功能整个关掉」，而审计信息还告诉他补位机制运行过。
  现有守门 `test_backfill_rounds_are_capped` 只断言 `roundsUsed == 1` 与出现了
  `rounds_exhausted`，**没有断言补位次数**，所以这个偏移测不出来。
- **修复方向**：把 break 挪到补位之后（或改成 `if rounds_used > max_rounds`），
  并补一条断言「`max_rounds=1` → `backfilled == 1`」。⚠ 若维持现状，
  必须改文案（不能说「已达上限」）并在参数包 schema 注释里写明它是「筛查轮数」不是「补位次数」。

### R2-06 · 没有冻结预案的票**不进** `k9_d1_verdicts` —— S17 的成立率分母会与 K9 §八 不符

- **修复方向**：要么 `ensure_rows` 按 **D0 清单全量**建行（无预案的行 `verdict` 恒 NULL 并加一个
  `no_playbook` 标记），要么在 §5.8.2 的铁律里明写「成立率的分母 = 清单，
  未冻结预案的票计入分母、不计入分子」。⚠ 建议与 §13 Backlog **B10** 一起在 **S17 开工前**定，
  两条都是「口径没定就先写渲染会返工」的同一类。

### R2-07 · `/review/bindery` 的 `preSessions`/`postSessions` 无上界；截断规则会把窗口挪到与成交日零重叠

- **文件**：`Backend/neckline/api/app.py:715`（`preSessions: int = -1, postSessions: int = -1`，
  只判 `< 0`）、`Backend/neckline/review/bindery.py:237-259`（`_sessions_around`）、
  `:326-331`（`start = span[-MAX_WINDOW_SESSIONS]`）
- **实测**：
  - `preSessions=postSessions=100000` → 窗口 `1643-03-06 → 2409-12-14`（200,005 个交易日），
    `_sessions_around` + `trading_days_between` 合计约 1.1 s；
  - `=350000` → 窗口 `0684-11-28 → 3368-03-21`（700,005 个交易日），**4.2 s / +42 MB RSS**；
  - 再大则 `timedelta` 溢出 `OverflowError`（被路由的 try/except 兜住，返回 `unavailableReason`）。
- **为什么是问题**：
  1. **正确性**：`MAX_WINDOW_SESSIONS=250` 的截断只动 `start`（取最后 250 根），`end` 不动。
     窗口被向后拉长时，截断后的 `[start, end]` 会**整段落在成交日之后**，
     那一周的每一笔回合都拿到 0 根 K 线，材料是空的（虽然逐条 `bars_missing` 有披露）。
     同样的形状在正常场景也会出现：一份跨度较长的交割单（早开仓、本周才平）会让早期回合
     被从最早处截掉。
  2. **容量**：这个端点跑在**常驻** `neckline.service` 上，而 §12 坑 1 与 §13 Backlog B5
     正在为 900 M 的 18% 余量发愁；一个来自查询串的整数就能让它多吃 40 M / 阻塞 4 s。
- **修复方向**：给两个参数一个上界（例如 `0 <= n <= MAX_WINDOW_SESSIONS`，超了 422），
  并把截断改成**围绕成交日区间** clamp（保 `[lo, hi]` 一定在窗口内）而不是「取最后 250 根」。

### R2-08 · 报告的「结构化完整版」不含解释层资料与预案 —— 它存在的理由正是这两样

- **文件**：`Backend/neckline/report/render.py:42-66`（`structured()` 的 17 个顶层键里没有

  market/packId/packVersion/paramsPackageVersion/relaxedCount/reportDate/run/state/strategy/
  strictCount/tradeDate`。默认视图的「### 逐只」段有这两样，折叠起来的 JSON 块没有。
- **为什么是问题**：§5.10 与架构 §3.5 给结构化完整版的用途是**「展开可整段复制到聊天框做深度分析」**。

### R2-09 · 早晨两拍在 **async 事件循环里同步阻塞**；拉价挂起时整个 API 停摆

- **文件**：`Backend/neckline/api/app.py:217`（`async def _morning_loop`）、
  `:246` / `:251`（两个 tick 都是**同步**调用，内部做 HTTP + SQLite）；
  超时账在 `Backend/neckline/data/realtime.py:53-55`（`connect=3s` / `read=5s` / `2` 次尝试）
- **事实**：单源最坏 `2 × (3+5) = 16 s`，双源顺序 → 单拍最坏约 **32 s** 完全阻塞事件循环；
  而收紧区间的轮询间隔是 **30 s**（`_MORNING_TIGHT_POLL_SEC`）。
- **为什么是问题**：9:26–9:29 与 9:55–10:06 正是用户盯着 App 看核对表的时刻。
  行情源抽风时，`/api/health`、`/api/checklist/{date}`、`/api/selection/latest` 会一起卡住，
  用户看到的是「App 转圈」，而服务端日志只说「实时源请求异常」。
  ⚠ 这是从 K8 `_sentinel_loop` 继承下来的形状，但 S8 把轮询从 5 分钟收紧到 30 秒
  （commit `5a52496`）之后，阻塞窗口与轮询周期开始**重叠**，性质变了。
- **修复方向**：两个 tick 用 `await asyncio.to_thread(...)` 丢进线程池（改动 2 行，
  它们本来就是纯同步、不共享状态；SQLite 走的是每次新连接）。
  ⚠ 别改成 `asyncio.create_task` + 同步函数，那不解决阻塞。
