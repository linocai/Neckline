## 1. 🔴 阻塞

### B1 · `freeze_pack` 跨 `pack_version` 静默覆盖同日 parquet ——「口径变了就发新版本」这条唯一逃生口自己就是覆盖后门

**位置**
- `Backend/neckline/facts/store.py:190-192`（`final_path = day_file_path(PARQUET_TABLE, pack.trade_date, root)` → `os.replace`）
- `Backend/neckline/data/market_data.py:84-86`（`day_file_path` 的路径里**没有** `pack_version`）

**问题**
`fact_packs` 有 `UNIQUE(trade_date, pack_version)`，即同一天允许两版清单行；但 parquet 的路径只有
`fact_pack/year=YYYY/YYYYMMDD.parquet` 一个坑位。于是给同一天冻结一个**新版本**时：
旧版本的清单行原样留着（连同它的 `content_fingerprint`），而它指向的 parquet 已经被新版本的数据覆盖。

**复现**（scratchpad 实测输出）

```
fp-2 fingerprint: b97065560e282a3e   close: [10.0]
fp-3 fingerprint: c70570e43e611a84   close: [99.0]
重新读 fp-2 清单行 → fingerprint: b97065560e282a3e
重新读 fp-2 的 rows(实际磁盘内容) close = [99.0]      ← 拿到的是 fp-3 的数据
同一个 parquet 路径? True
磁盘 sha256 与 fp-2 清单指纹一致吗? False
```

**为什么是问题**
- §5.3.2 纪律 3 逐字：「口径变了就**发新 `pack_version`**，⛔ 没有静默重写这条路」。
  实际上那条**被指定为正路**的路径，正是唯一能把旧数据抹掉的路径。
- 架构 §3.1 / §5.3.2 第 6 条：「成绩单永远记得自己跑在哪版事实包」。`k9_runs.pack_id` 指过去，
  读回来的却是另一版的行 —— 记账物在说谎，而这正是 §5.3.2 纪律 2 花力气避免的那种事
  （「反序则会留一个指向空气的清单 —— 那是审计物，不能允许它说谎」）。
- §5.13：「标定必须跑在与生产**逐字节相同**的事实包上」。`export_research_snapshot --include-fact-packs`
  的逐日 sha256 会与旧版本清单行的指纹对不上。
- **不是假设**：本版已经把 `PACK_VERSION` 从 `fp-1` 升到 `fp-2`（裁定 12）。任何存在过 fp-1 包的环境
  （开发机、whynotme 快照），只要重跑过 fp-2，fp-1 的数据就已经没了。

**顺带**：重复检查（`store.py:164-172`）发生在写 parquet **之前**，`os.replace` 在插清单**之前**。
两个进程并发冻同一 `(date, version)` 时，后到的那个会先把文件覆盖掉，再在 INSERT 处吃到 `IntegrityError`
并抛 `PackAlreadyFrozen` —— 已经落地的那份 parquet 与先到者的指纹从此对不上。

**修复方向**
1. 把 `pack_version` 写进 parquet 路径（如 `fact_pack/version=fp-2/year=YYYY/YYYYMMDD.parquet`），
   或者退一步：`freeze_pack` 发现该日已有**其它版本**的 parquet 时拒绝就位并指明冲突。
2. 补一条守门：同日先冻 fp-2 再冻 fp-3 → 断言两版都读得回来，且**各自**的 `content_fingerprint`
   都等于自己那份磁盘文件的 sha256。
3. 并发那一半：把重复检查和 INSERT 收进同一个事务，或者干脆先 INSERT 占位再写 parquet。

### B2 · 全部导入边界守门对**相对 import** 全盲 —— G1 / G2 / G3 / G4 / G5 / G7 / G18 一起漏

**位置**
- `Backend/tests/guard_scan.py:36`
- `Backend/tests/test_v250_s6_k9_guard.py:44`
- `Backend/tests/test_v250_s5_params_guard.py:61`

三处扫描器同一句：

```python
elif isinstance(node, ast.ImportFrom) and node.module and not node.level:
```

`node.level > 0` 就是相对 import。这一句把它们全部跳过了。

**复现**（在只读副本上，两条都是全绿）

| 反例 | 结果 |
|---|---|
| `neckline/k9/run.py` 里加 `from ..data import market_data` + `from ..llm import factory` | `test_v250_s5_params_guard.py` + `test_v250_s6_k9_guard.py` **40 passed** |
| `neckline/facts/pack.py` 里加函数内 `from ..k9 import ranks` | `test_v250_s3_facts_guard.py` **21 passed** |

**为什么是问题**
§5.2 那张表的全部承诺是「四条边界怎么被**结构性**保证（不是靠注释提醒）」，§3.2 也把「守门方式 = AST 扫描守门单测」
定死为技术选型。这两条承诺完全落在这三个扫描器上。改一个 import 的写法就能穿过去，
而且**穿过去之后测试是绿的** —— 这比没有守门更危险，因为它会让下一个人相信边界还在。

受影响的是 §10 里的 G1 / G2 / G3 / G4 / G5 / G7 / G18 / G19，其中：
- **G3（`k9/**` 不 import `tushare_client` / `market_data`，「取数唯一来源是事实包」的真牙齿）没有任何第二道防线。**
- G2（零 LLM）尚有 `test_the_whole_chain_runs_with_the_llm_factory_rigged_to_explode`
  （`test_v250_s6_k9_guard.py:367`）在运行期兜着，但那只证明「这条夹具路径上没调到」，不证明没有调用点。

**修复方向**
1. 去掉 `not node.level`，按文件所在包把相对 import 解析成绝对模块名再比对。
2. 给每个扫描器补一条**自检**：造一个含相对 import 的临时文件，断言扫得到
   （体例仓里已经有，见 `test_the_offender_detector_actually_detects` / `test_the_mean_volume_detector_actually_detects`）。
3. 顺手加一条「`neckline/**` 一律绝对 import」的守门 —— 全仓目前只有 `neckline/search/__init__.py:3` 一处相对 import，
   代价近乎为零。

### H1 · 参数包校验：窗口类键被声明成 `float`，整数性 / 正数 / `MAX_LOOKBACK_PACKS` 三道闸一起失效

**位置**
- `Backend/neckline/k9/params.py:346-349`
  ```python

      ch: {tier: {k: float for k in keys} for tier in _TIER_NAMES}
      for ch, keys in _CHANNEL_TIER_KEYS.items()

  ```

- `Backend/neckline/k9/params.py:474-484`（`_check_ranges`）：`_POSITIVE_INT_PATHS` 与 `_WINDOW_PATHS`
  两个循环都用 `isinstance(v, int)` 做前置判断 —— 值是 float 就**整条跳过**。

**复现**（`P.validate()` 的返回）

| 输入 | 结果 |
|---|---|
| `channels.p3.strict.longWindow = 500.0` | `missing=[] invalid=[]` ← **通过** |
| `channels.p2.strict.maDays = 0.4` | `missing=[] invalid=[]` ← **通过** |

**为什么是问题**

  于是裁定 5 那条「参数未配置 = 今天没跑成」的三态映射在这些输入上走的是异常路径，不是 `not_run`。
- `longWindow = 500.0` 只剩 `run.py::required_lookback`（`run.py:120-125`）一道拦。§12 坑 1 的容量红线
  （2 vCPU / 1.6 G，700M cap 被 OOM-kill 过）本该在参数校验就挡住。

**修复方向**：`_CHANNEL_TIER_KEYS` 不能只是键名元组，要带类型（`*Days` / `*Window` → `int`）；
`_check_ranges` 遇到 int 路径上出现非 int 值时直接判 `invalid`，⛔ 不是跳过。

### H2 · 阈值键没有下界 / 区间校验 —— 一个写错的标定值会安静地跑出一份错清单

**位置**：`Backend/neckline/k9/params.py:394-400`（`_UNIT_INTERVAL_PATHS` 只覆盖
`boundary.liquidityBottomPct` + p4 的两个 `*RankPct`），`:490-495`。

**复现**（全部 `missing=[] invalid=[]`）

| 输入 | 后果 |
|---|---|
| `volume.eruptionMultiple = -1` | p1 的 `≥ V` 对全体成立、p3 的 `< V` 对全体不成立 → **形态 3 当天归零**、形态 1 的放量门槛整条失效 |
| `channels.p2.strict.minVolMultiple = -1` | 裁定 13 的「有实际换手」失效 |
| `channels.p1.strict.ampMaxPct = -5` | p1 永远召不到票 |
| `channels.p4.strict.lagRankGap = 7` | p4 永远召不到票（百分位差值最大是 1） |

**为什么是问题**
§5.4.3 校验 2 原文是「**类型 / 区间**」，现在区间只做了一半。而这几个错值**不会**变成
「今天没跑成」—— 系统照跑，报告只会说「今日无此形态」（K9 §五-5 的诚实缺席），
看不出是参数写错了。裁定 5 建立的「跑通了、结果为空、可以被信任」这条语义在这里被稀释。
`lagRankGap` 尤其应当补：p4 模块 docstring（`p4_moneyflow.py:21-25`）与 §14 S6 登记 ① 都明写它是 0~1 的差值。

**修复方向**：`eruptionMultiple` / `minVolMultiple` / `normDropMin` / `flatBand` 加 `> 0`；
`lagRankGap` 进 `_UNIT_INTERVAL_PATHS`（或 `[0,1]` 闭区间）；`ampMaxPct` / `minRetPct` /
`spikeFade*` 至少加一个百分点合理区间。

### H3 · `k9/volume.py:39 _MIN_COVERAGE = 0.5` —— 一个未登记、会改变召回的自定量

**位置**：`Backend/neckline/k9/volume.py:39`，用在 `:73` 与 `:88`。

**问题**
它决定「历史要有多少天才给出放量倍数」。取 0.5 意味着：20 日窗口里只有 10 天历史的票，
拿 **10 天均量**当分母，却和满窗的票共用同一个 `vol_multiple` 名字与同一个门槛 V。

**实测**（scratchpad，`ma_days=20`）

```
AAA（19 天历史，日均 100，当日 250） → vol_multiple = 2.5
BBB（10 天历史，日均 100，当日 250） → vol_multiple = 2.5
```

**为什么是问题**
1. 放量倍数正是 p1 / p3 的**分界**（裁定 15），也是 p2「有实际换手」的判据 —— 这个数直接决定谁进哪个形态。
2. 它不在 §8 的待标定总表里，也**不在 §14 S6 的登记清单里**。S6 那条把 p1 振幅形状、p3 窗口形状、
   p4 排名口径、`count` 归一、缺读数重新归一五处判断都如实登记了，唯独漏了它。
   对照全局经验条「定性需求不许自作主张定量（用户当场批评，代价 = 返工两轮）」，这是同一类。
3. 与同组三个模块不一致：`p2._prev_close_and_ma`（`p2_rebound.py:131`）要满窗、
   `p3._window_sum`（`p3_riser.py:80-83`）要满窗、`p4._cum_inflow`（`p4_moneyflow.py:55-56`）要满窗，
   只有放量倍数收半窗。

**修复方向**：改成「满窗才给读数」与其余三处一致（零新增数，最省事），
或者作为一条登记项摆出来交标定侧拍板。⛔ 不要施工侧继续替它选值。

### H4 · `boundary._liquidity_cut` 的「20 日平均成交额」在历史不足时是**半段窗口均值**，而 docstring 说的是 null

**位置**：`Backend/neckline/k9/boundary.py:90-103`（`group_by("ts_code").agg(mean)`，没有任何 `_n >= window_days` 过滤）
对照它自己的 docstring `:82-84`：「历史不足 → 均值为 null → **不排除**」。

**实测**：一只只有 11 天数据的票，拿到的是 11 天均值，照样参与全市场分位排名（不是 null）。
docstring 描述的行为只在**零行**时成立。

**为什么是问题**
K9 §二 第 7 条逐字是「**20 日**平均成交额位于全市场后 20%」。一只刚复牌 3 天的票拿 3 天均量
去和 5500 只票的 20 日均量比分位，排出来的名次没有意义，而这条排除项决定它进不进池。
方向也不确定（3 天恰好放量 → 排名虚高不被排除；3 天恰好缩量 → 被误排）。

**修复方向**：与 p2/p3/p4 一致加 `_n >= window_days` 过滤，不足者不排除
（这才是 docstring 已经承诺的行为），补一条夹具。

### H5 · `relaySource='shortlisted'` 只读 `primary_pattern`，丢掉那天命中的其余形态

**位置**：`Backend/neckline/k9/store.py:453-455`

```python
sql = (f"SELECT trade_date, ts_code, primary_pattern FROM {LISTING_TABLE} "
       "WHERE trade_date>=? AND trade_date<=? AND strategy=?")
```

**问题**
`k9_listing_entries` 明明有 `patterns_json`（写入在 `store.py:184`，正是 K9 §五-4「命中的形态全部列出」），
接力分却只拿主形态。于是：一只票 D−3 同时命中 p3/p4（`primary_pattern = p3`）、今天又命中 p3，
`ranking.relay_counts`（`ranking.py:186-188`）会因为 `r.pattern in mine` 而跳过它 —— 那份 **p4 的证据被吞掉**。

**为什么是问题**
K9 §四 的跨日接力分依据是「**发生在不同日子的两份独立证据**」。`shortlisted` 这一档系统性偏低，
而 `recalled` 那一档读的是 `k9_channel_hits` 的**全部**召回记录 —— 两个取值因此**不可比**。
§8.3 #19 把 `relaySource` 降为「取值待标定」，标定侧要在两者之间选一个，
拿一个被压低的口径去比另一个，会得出错的结论。

**修复方向**：`shortlisted` 分支改读 `patterns_json` 并展开；补一条夹具，
断言两个 source 在同一份历史上对同一只票数出的「其它形态」集合一致。

## 6. 我认为**没问题**的关键点（⛔ 后续 builder 不必重复怀疑）
