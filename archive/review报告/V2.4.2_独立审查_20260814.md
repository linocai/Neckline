### P1 - 发布路径不是原子事务，失败时会让未发布的篮子事实被报告读侧看见

- 位置：
  - `Backend/neckline/report/evening.py:566`
  - `Backend/neckline/report/evening.py:599`
  - `Backend/neckline/report/evening.py:607`
  - `Backend/neckline/report/pipeline.py:255`
  - `Backend/neckline/report/basket_daily.py:652`
  - `Backend/neckline/report/basket_daily.py:678`
- 触发条件：`_run_basket_segment()` 在 `save_tier_decision()` 成功后、`save_basket_cards()` 或 `finish_run(... published=True)` 之前失败，或者卡保存失败后报告段继续执行。
- 证据：
  - `evening.py:566` 先把 `baskets/basket_members/tier_history` 写入。
  - `evening.py:599` 之后才写 `basket_cards`。
  - `evening.py:607` 最后才把 selection run 标记为 published。
  - 报告段 `pipeline.py:255` 调 `build_basket_daily()`，读侧 `basket_daily.py:652` 直接从 `baskets` 读今日篮子；没有卡时 `basket_daily.py:678` 显示 `card_not_ready`。
  - 临时库复现输出：

```text
{'baskets_available': True, 'basket_count': 1, 'first_card_unavailable_reason': 'card_not_ready', 'selection_state': None}
```

- 实际影响：V2.4.2 计划要求“一次短 publish transaction 写 terminal basket/tier/card/report facts 并标记 run published”，且 `processing/unavailable` 不能替换上一份完成快照。当前实现仍会在发布中段失败后暴露新一批未完成事实，用户可能看到“今日有篮子但卡未就绪”的半成品，而不是继续看到上一份完整快照或明确 unavailable。
- 最小修复方向：引入 run-scoped staging 或 `published_run_id/generation_id` 过滤，所有读侧只读取已发布 run 的最终事实；或者把 `baskets/tier_history/basket_cards/reports/selection_runs.published_at` 的可见性放进同一个短事务。不要让 `baskets` 的存在本身等同于已发布。

### P1 - 补位停止点放在六关之前，候补池不会在真实合格数不足时继续补位

- 位置：
  - `Backend/neckline/selection/direction_pipeline.py:318`
  - `Backend/neckline/selection/direction_pipeline.py:330`
  - `Backend/neckline/selection/aggregate.py:2577`
  - `Backend/neckline/selection/aggregate.py:2584`
  - `Backend/neckline/report/evening.py:464`
  - `Backend/neckline/report/evening.py:487`
- 触发条件：首批 deep reason 产出达到 `sufficient_candidate_count`，但后续 `_gate_proposal()`、证据白名单、六关或 Tier 把其中大量方向拒掉。
- 证据：
  - `direction_pipeline.py:318` 只要 deep reason JSON 解析成功就加入 `proposals`。
  - `direction_pipeline.py:330` 用 `len(proposals) >= cfg.sufficient_candidate_count` 直接停止补位。
  - 真实候选资格在管线返回之后才发生：`aggregate.py:2577` 调 `_gate_proposal()`，`aggregate.py:2584` 可能 reject；`evening.py:464` 跑六关，`evening.py:487` 才 Tier。
- 实际影响：用户要求的是“深度研究后如果合格候选不足，则从候补池继续补位”。当前合格的定义实际变成“LLM 返回了语法完整 JSON”，不是“通过机械白名单、证据、六关与容量后的可发布候选”。首批 20 个如果大面积被机械或六关剔除，系统会停止，不再从候补池补足。
- 最小修复方向：把补位循环提升到 aggregate/evening 能看到机械白名单和六关结果的位置；每批 deep reason 后先 `_gate_proposal()` + gates/tier 预判，再按已合格候选数决定是否继续从 reserve/normal 补位，并把每轮补位原因写入 run events。

### P2 - 逐级审计链断裂：事件没有关联 LLM call，也没有 gate/tier/freeze/final disposition

- 位置：

- 触发条件：任意 V2.4.2 selection run。
- 证据：

  - `triage_*`、`research_complete`、`reasoning_complete` 事件在 `direction_pipeline.py:218/273/324` 均未填 `llm_call_id`。
