## Findings

### P1-1｜方向 sidecar 的“一包最多一次外部调用”不具备并发幂等

证据：

- `Backend/neckline/facts/direction_llm.py:60` 先读 `direction_store.load(pack.pack_id)`，不存在才继续。
- `Backend/neckline/facts/direction_llm.py:70-72` 在没有任何抢占/占位记录的情况下直接调用 `provider.chat(... enable_search=True ...)`。
- `Backend/neckline/facts/direction_llm.py:80-81` 调用后立即写用量账。
- `Backend/neckline/facts/direction_store.py:38-46` 的 `INSERT OR IGNORE` 发生在外部调用之后，只能避免重复 sidecar 行，不能避免重复 Tavily/DeepSeek 调用。
- 我用临时 SQLite DB 和慢速 mock provider 做双线程复现，结果为：`provider_calls=2`、`usage_events=2`、`sidecars=1`、两个线程均返回 `ready`。没有真实外部调用、没有生产库写入。

触发条件：两个晚间链路、手动补跑、systemd 重入或运维误触发在同一 `pack_id` 的第一条 sidecar 写入前同时进入 `run_once`。

实际影响：违反执行计划“每个 pack 一次 logical Tavily/LLM”的成本边界；会产生重复外部费用和重复 `market_direction` 用量账，但最终 sidecar 只有一条，导致成本审计与事实包追踪不一致。

最小修复方向：在外部调用前用唯一主键原子 claim 该 `pack_id`，例如先插入 `not_attempted/running` 占位行或独立 claim 状态；只有抢到 claim 的进程调用 Tavily/LLM，其他进程重读已有状态。补一个并发测试，断言同一 `pack_id` 双线程只产生一次 provider 调用和一次真实调用用量事件。

### P1-2｜离线缓存会掩盖服务端错误或坏响应，把旧报告冒充为可读缓存

证据：

- `App/Neckline/App/AppModel.swift:351-358` 成功解码后保存 selection 快照，这部分正常。
- `App/Neckline/App/AppModel.swift:359-373` 失败分支只排除了 `APIError.unauthorized`；除此之外，只要本地有缓存就回退到 `snapshotStoreProvider()?.latest()`。
- `App/Neckline/Networking/APIClient.swift:175-177` `fetchSelectionLatest()` 会在 `JSONDecoder().decode(...)` 失败时抛出非 `APIError` 的解码错误。
- `App/Neckline/Networking/APIClient.swift:473-492` 400/404/409/422/500 等服务端明确错误都会以 `APIError.server/notFound/validation` 抛出。
- 执行计划明确要求：网络不可达才可用缓存；`401/凭据缺失/响应损坏/服务器明确 not_run` 不可回退旧缓存（`archive/施工图/V2.5.1_Build11_执行计划_20260823.md:107-108`）。

触发条件：服务端返回 500、404/422、坏 JSON、schema 解码失败，且同 namespace 下已有旧 selection 快照。

实际影响：App 会显示旧报告并标记“离线浏览”，`loadError` 被清空。用户看到的可能不是当前服务端状态，尤其会掩盖服务端真实故障或响应契约破坏。这与本版“不把旧缓存冒充新报告/不把网络错误说成空清单”的目标冲突。

最小修复方向：只允许明确的传输层网络不可达错误回退缓存，例如 `APIError.transport` 且语义为无网络/连接失败；解码错误、4xx/5xx、validation、notFound、unauthorized、未配置凭据都应直接展示错误，不读旧缓存。补两个客户端状态机测试：缓存 + 断网应回退；缓存 + 500/坏 JSON 不得回退。

### P2-1｜`playbook` 用量事件缺少 `pack_id`，四类调用无法完整按事实包追踪

证据：

- `Backend/neckline/report/evening.py:436-442` `_run_playbook` 只加载 `listing`，调用 `fill_for_listing(... report_date=report_date, db_path=db_path)`，没有传 `pack_id`。
- `Backend/neckline/playbook/fill.py:259-263` `fill_for_listing` 接受可选 `pack_id`，默认是 `None`。
- `Backend/neckline/playbook/fill.py:287-290` 将这个默认 `None` 继续传入 `fill_one`。
- `Backend/neckline/playbook/fill.py:186-187`、`:200-205` 的 `usage.record(task="playbook", ...)` 最终会写入 `pack_id=None`。
- `Backend/neckline/k9/store.py:350-375` 已有 `load_run()` 可以从当日 K9 run 读取 `pack_id`，但 `_run_playbook` 未使用。
- 执行计划要求 `llm_usage_events` 每行包含 trade/report/pack 关联（`archive/施工图/V2.5.1_Build11_执行计划_20260823.md:55-58`）。

触发条件：正常晚间链路生成定稿清单后进入预案填值，任何 playbook LLM 调用都会落账。

实际影响：按日期和任务聚合仍可看，但按事实包追踪不完整；当同一交易日存在补跑或不同事实包时，无法准确回答“这笔预案 LLM 成本属于哪个 pack”。这是审计链路缺口，不直接改变 K9 结果。

最小修复方向：`_run_playbook` 在加载 listing 后读取 `k9_store.load_run(trade_date, db_path=db_path)`，将 `run["pack_id"]` 传给 `fill_for_listing`；若 run 不存在则继续 `None` 并记录可读原因。补测试断言正常链路的 `playbook` usage row 带有 `pack_id`。
