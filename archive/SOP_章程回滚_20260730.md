# 章程回滚 SOP(v1.5-④-A5,§七 P1-24 结案)

> **诚实边界(写在文首,不得删,原条"别凭空编"的精神保留)**:本 SOP **未经实战演练**——
> 是 2026-07-30 基于代码侧已确认的事实(`scripts/activate_charter.py`/`brain.py` 的append-only
> 事件流语义 / 既有同步纪律)整理出的操作手册,不是"已经用过、踩过坑"的经验总结。
> **首次真回滚发生后,必须按实际经历修订本文件**(哪一步卡壳、哪个同步点漏了、耗时多久、
> 有没有本文没预料到的情况)——只写已知事实与同步清单,不编造未验证的操作细节。

## 一、什么情况该回滚(判据,不是感觉)

回滚 = 用 `activate_charter.py` 把 `is_active` 切到**此前已经现役过**的一个版本(触发脚本内
「重激活/回滚」告警);不是新造一版章程,是回到旧版本。三类场景,判据从硬到软:

1. **客观配置错误(应立即回滚,无需犹豫)**——激活后发现 `brain.get_active().rule` 的实际
   内容与 `PROJECT_PLAN.md §2.1`/`STRATEGY_LAB.md` 记录的"应该是什么"不符(如
   `_CORE_EXPECTATIONS` 核对表本身配错、或手误激活了错误的目标行)。**判据是逐字段对照,
   不是感觉"好像不对"**。
2. **实盘归因证明这版参数明显更差(需要与激活同等的严谨度,不能单凭直觉切)**——
   §2.6「策略进化门禁」要求任何章程变更须过回测 + walk-forward 样本外 + 用户批准;回滚
   同样是一次章程变更,理应有类似量级的证据支撑(而不是"感觉最近老止损"这种未经归因的
   印象)。已有先例:`activate_charter.py` 把 `v1.3` 保留为「唯一合法回退目标」,正是为
   "v1.3.3 拆墙如被证明弊大于利,需要恢复高弹禁买墙"这个具体场景准备的。
3. **紧急止损(先回滚稳住,再补分析)**——怀疑当前激活的章程正在实时造成资损(如某个
   参数错误导致止损价/仓位上限算错),可以先回滚到上一个已知良好版本止血,**但事后必须
   补一次强制复盘**(复用 §2.1 第 4 条同款机制:材料由系统生成,说明回滚原因与影响范围)
   ——先止血不等于不用交代,紧急动作事后同样要交代清楚。

**不构成回滚理由**:短期噪音(如"这周单笔超限的假警报",已知是"按周判纪律"的展示层局限,
不是章程本身的问题,见 §七 P1-4)、单笔亏损(纪律的作用就是控制亏损分布,不是消灭亏损)。

## 二、操作序列

回滚**只走命令行**,不做 API 端点(§3.8「策略大脑激活绝不暴露给客户端」)。生产环境执行者
= 能写权威 SQLite 库的身份(`sudo -u neckline`);本地开发库任何人都能跑,不影响生产。

1. **确认目标版本合法**:回滚目标必须在 `activate_charter.py::_ALLOWED_TARGETS` 白名单内
   (当前 `("v1.3", "v1.3.3")`)。若要回滚到的版本不在白名单(如某个已被否决的 K 字头研究臂,
   或更早的 `v1.2`)——**先别改脚本仓促上线**,这本身是一次代码变更,须回 planner 走一遍
   「要不要把它重新列为合法目标」的讨论,不是回滚这个动作本身该决定的事。
2. **双备份(高危区标准动作,回滚同样适用)**:`sqlite3 .backup` + 另 `cp -p` 一份(命名
   `neckline.db.{bak,cpbak}-rollback-<date>-<time>`),这是本项目对任何触碰权威库动作的
   一贯要求(见 CLAUDE.md「生产实战定案」节),回滚不因为"是切回旧版本"就降低标准。
3. **Dry-run 先看 diff**:`python scripts/activate_charter.py --target <目标版本>`(不带
   `--confirm`)。核对打印出的四道闸信息——① 目标合法性;② 是否有 `open` 持仓(有则看闸 2
   窄豁免是否适用,豁免只在 diff 落在 `_ENTRY_SIDE_EXEMPT_KEYS`〔目前仅
   `forbid_high_elasticity`〕且退出/仓位八项不变时成立,否则须先清仓);③ old→new 逐字段
   diff + 核心值核对;④ 若目标此前激活过,会看到「⚠ 重激活/回滚」告警横幅(列出此前激活
   过几次、每次何时)。**diff 与告警都读懂、都认可了才进下一步。**
4. **确认执行**:`--target <目标版本> --confirm`。若涉及闸 2 窄豁免或重激活告警,脚本会把
   对应留痕**追加**写入 `<db 同目录>/charter_activation_audit.log`(写不成 → 闸 2 豁免场景
   直接拒绝激活;重激活场景只告警不拦,但要手动把这次回滚记进 §九)。
5. **验证结果**:脚本自己会断言激活后 `is_active` 恰为目标版本且唯一;额外人工核对
   `brain.get_active(db_path=...).rule["config"]` 与预期逐字段一致。

**append-only 事件流语义(必须理解,不是"回滚就是把时钟拨回去")**:`strategy_activation_log`
只在时间轴**末尾追加**一条新事件,永不改写、永不删除、永不移动此前任何一条事件;
`config_governing_at`/`config_governing_for_week`/`config_active_at` 三个时间线解析器都基于
这条链回答"某个历史时刻/历史周,当时现役的是谁"。**回滚之前每一段治权的逐笔纪律判定逐位
不变**(v1.4 review 🟡-1 修复的直接效果,反例单测
`test_rollback_reactivation_does_not_whitewash_history` 锁死)——回滚不会让"回滚前那段时间
里,某笔超限的成交"变得不再超限,历史判定不因回滚被洗白。

## 三、同步清单

回滚是一次真实的生产/纪律动作,不能只落在 DB 里就算完:

- **`STRATEGY_LAB.md` §一「现役与机制」**:该行标注的是 **K 字头**血缘(如"现役策略 =
  K1"),**不是** v 字头章程编号。当前所有系统线章程行(`v1.2`/`v1.3`/`v1.3.3`)都同宗
  K1——纯粹的仓位/退出参数回滚(如 v1.3.3→v1.3)**不需要**改这一行。只有回滚牵涉切到不同
  K 血缘(理论上不该发生,K 字头研究臂根本不在白名单内)时才需要同步,操作前先判断这一条
  是否适用,别无脑照抄"改现役标注"这一步。
- **`PROJECT_PLAN.md §2.1`**:纪律章程文字本身若因回滚而与"现行值"描述不一致,须补一行
  说明(如回到 `v1.3` 意味着 `forbid_high_elasticity` 重新变 `True`,§2.2 那条"拆墙自
  v1.3.3 起解除"的批注需要追加"已于 <日期> 回滚,高弹禁买墙重新生效"这类说明,而不是
  删掉原批注——原批注是历史决策记录,不是"当前状态"字段)。
- **`PROJECT_PLAN.md §四(当前状态)`**:快照制,本节**替换**写清"现役章程 = <回滚后的
  版本>"及回滚理由一句话。
- **`PROJECT_PLAN.md §九`**:变更日志一行(日期 · 回滚动作 · 理由 · 授权方);若是紧急止损
  式回滚,事后的强制复盘材料写 `archive/` 独立文件,§九 一行 + 链接。
- **`~/hz_info.md`**(仅当动的是生产库):按既有惯例记一条运维事实——回滚后的对外版号 /
  `is_active` / `activated_at` / 影响的字段,不写敏感内容。

## 四、要不要重跑受影响周的复盘

**判据**:回滚生效时刻(`strategy_activation_log` 新追加那条事件的 `activated_at`)是否落在
**已经生成过复盘**的那一周区间内。

- **落在已生成复盘的周内 → 需要重跑**,否则那份报告的 `charterSegments`/`charterSwitches`/
  `strategy_version` 标签不会反映这次切换(它们是生成时刻的快照,不会因为 DB 后来变了而
  自动刷新)。**方法 = 重新上传同一周的交割单**(`POST /review/upload`,或客户端周复盘
  上传入口)——`reviews` 表按 `week` 主键 `INSERT OR REPLACE`/`ON CONFLICT DO UPDATE`
  幂等覆盖(见 `review/store.py::save_weekly_review`),不会留重复行,重跑安全。
- **落在尚未生成复盘的周内(如刚开盘就回滚、或本周还没上传交割单)→ 不需要手动重跑**,
  下一次正常上传交割单时,`config_governing_at` 自然会读到最新的激活时间线。

**这不是正确性问题,是展示层问题**:逐笔纪律判定本身不会因为"要不要重跑"而不同——
append-only 事件流保证不管重跑与否,`config_governing_at(某笔真实成交时刻)` 给出的答案
都是同一个(见 §二 事件流语义)。"要不要重跑"决定的只是"已经生成过的那份报告文件里,
`charterSegments` 这类展示字段是否显示最新状态",不影响审计结论本身。
