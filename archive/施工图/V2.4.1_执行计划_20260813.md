# V2.4.1 macOS 选股工作台执行计划

> Status: Released on 2026-08-14. Authority order: current user decisions in this thread, then `PROJECT_PLAN.md`; this document is the completed execution record. The prior `App/V2.4.1_FRONTEND_MEMO.md` is superseded and deleted.

## Outcome and non-goals

The macOS selection tab becomes one calm workbench: the sidebar chooses content; the right pane explains it. A user can see every basket member, select any member, understand one basket without decoding system internals, and move to market, auction, or intelligence without losing context.

Out of scope: iOS/iPad layout changes, the Review tab, holdings redesign, strategy/gate/scoring changes, research/backtest code, new LLM calls, production data writes, deployment, upload, notarization, or distribution.

All work is directly on `main`; this release creates no branch.

## Product contract

### 1. One macOS selection state

Introduce one explicit destination state in `AppModel`, owned by the selection tab:

| Destination | Sidebar state | Right pane |
| --- | --- | --- |
| `market` | Today Market is selected | Market status, sentiment, sector context, readable data condition |
| `auction` | Auction Report is selected | Full report in reading order |
| `basket(id)` | That basket is selected | Basket overview, all members, selected-member detail |
| `intel` | Today Intel is selected | Intelligence package, moneyflow, news |

- Opening the Selection tab defaults to **Today Market**, visibly highlighted. A user click is the only way to change destination, except a valid deep link/QA hook that selects its exact destination.
- The existing `openedBasketId` may remain as a compatibility/deep-link input, but cannot be a competing presentation state. On macOS it must map into the single destination.
- iOS retains its current navigation/sheet behavior. Shared model additions must be inert there unless needed to decode additive fields.

### 2. Sidebar

- Header is compact; remove the duplicated long subtitle, raw global versions, basket score, truncated basket description, member price range, `OUT`, D0/D1, and technical disclosures.
- Top navigation contains Today Market, Auction Report (only when available; otherwise an honest compact unavailable state), and Today Intel. It shows meaningful status/counts, not report bodies.
- Keep T1/T2 groups and six-gate light summary. A basket row shows its display name, gate summary, count, then direct member rows with **name, one user-facing role, code**. No price range or raw `RS #` in this layer.
- A missing basket name displays `未命名篮子` / `篮子名称暂缺`, never `basket_key`.
- The bottom non-selected summary is one human sentence only when it has content, e.g. “另有 2 只未进入篮子，主要因为市场环境不匹配”; exact gate codes belong in technical details.

### 3. Basket and member detail

Right-pane basket order is fixed:

1. basket title and a single plain-language introduction;
2. vertical all-member selector;
3. selected member: name, code, a resolved role (or `角色待确认`), one current/frozen-price value, readable industry rank, and one selection reason;
4. `为什么是现在` and one material `待确认`/risk;
5. selected member’s three price references: 建仓观察区间、最高追价、离场参考区间;
6. explicit detailed-analysis entry, then a separate technical/audit entry.

- “现价” is used only for a live quote. The present frozen D0 close must be labelled as a close/reference price rather than being presented as live.
- Use existing `coreMetrics.industry_ret_rank_1d` and `industry_member_count` to render `行业今日表现第 n / N`; absence is honestly unavailable. Never display `industry_lift` in user/detail layers.
- Use existing driver/why-now/reason fields with deterministic trim/fallback. Strip display-only raw suffixes such as `policy`; do not call an LLM.
- Remove `NKMemberScaleBar` from the basket workflow. Delete the component only when its references are zero.
- All roles expose the product conclusion. Mechanical/LLM disagreement is an explicit “待确认” explanation in detailed analysis, not two default-layer badges.
- Convert the existing information card into an embedded member-detail surface on macOS. It may retain charts and evidence, but it is no longer a full-screen modal and does not repeat the entire basket context. Raw source keys and chart data are explicit technical content; basic chart hover/crosshair must expose date/OHLC/volume for the K-line.

### 4. Today Market, Auction Report, and Today Intel

- **Today Market:** use human labels plus deterministic summaries derived from current fields. `regimeReason` and raw `quotaReason` never render in default/detail UI. Express threshold context as a conclusion (“炸板率已高于风险线”), not a legend users must decode.
- **Auction Report:** remove modal-only presentation on macOS and no longer render an in-pane Close button. Start with title, human date/freeze window, overall conclusion, basket conclusions, member performance, material risks, and manual observation. Rename `逐票读数` to `成员表现`; move key/context domain, source ledger, LLM stage, historical sample machinery, and raw checks to one folded `数据说明与技术附录`. Repeated notice appears once at its highest relevant level.
- **Today Intel:** is a full right-pane destination. Keep scan-state honesty and “拥挤情报、非选股信号”; render large moneyflow in readable units (e.g. 亿元), make listed/available counts agree, and translate `10cm`/`20cm` to percentage-limit language. Do not repeat “参考” on every row when the section already states it.
- Standardize the right pane to a readable max content column/grid, consistent card widths, and meaningful 12–14pt secondary copy. Ten/eleven-point low-contrast text is reserved for true technical metadata.

### 5. Shared and edge states

- `MarketRegimeStrip` has a human default mode and a deliberate audit mode. Positions uses the default mode, so it no longer displays `rot.old_5d=…` or other machine expressions.
- Remove selection-state duplication from the global macOS toolbar: no market pill, strategy/pack string, freshness duplicate, or basket count badge. Preserve global tab navigation, refresh, and settings.
- User-facing loading/empty/error text describes availability and next action; it does not display `card_not_ready`, `card_corrupt`, `llm_stage`, raw error codes, or internal pipeline segment names.
- Default, detail, and technical layers must keep the difference between “no result”, “not run”, and “unavailable”; simplifying the words must not falsify the state.

## Minimal backend display contract

The service remains read-only and does not change any selection logic.

1. **Auction risks:** `clamp_risk_note` and `evidence_conflict_note` receive/display a basket name, not `basket_key`. For legacy frozen payloads, the client replaces a known key with the payload basket name and otherwise uses a generic human fallback; it never renders the key in a user layer.
2. **Tag absences:** preserve legacy raw `tagsAbsent` for compatibility/audit and add an additive labeled collection such as `tagAbsences: [{ code, label }]` to basket-card and info-card public DTOs. Labels originate from `member_tags.tag_label`; no client duplicate mapping. If old data lacks labels, default UI says only that some labels could not be judged because data is missing; codes remain audit-only.
3. **Existing frozen card compatibility:** all new Swift fields use `decodeIfPresent`; no storage migration and no reinterpretation of historical scoring/strategy facts.

## Execution stages

### A. Build the workbench and contracts

1. Add the explicit macOS destination state and QA hook; remove the implicit first-basket fallback.
2. Rebuild the sidebar and right-pane routing without changing iOS routes/sheets.
3. Rework basket/member hierarchy and refactor the information-card content for embedded macOS use; remove the basket scale bar.
4. Rework market, auction, and intel content to the three-layer model; fix the shared market string in both Selection and Positions.
5. Make additive backend display-contract changes and client decoding/fallbacks.
6. Add narrow tests for destination synchronization, no raw user fallbacks, labels, auction display names, and old-payload compatibility. Update generated Xcode project only after its source manifest changes.

### B. Build verification before review

Run from the documented directories:

```bash
cd Backend && .venv/bin/python -m pytest -q
cd ../App && xcodegen generate
xcodebuild -project Neckline.xcodeproj -scheme Neckline -destination 'platform=macOS' test
xcodebuild -project Neckline.xcodeproj -scheme Neckline -destination 'platform=macOS' build
```

Also run the existing API smoke script only against a temporary development database or explicit read-only snapshot; never fall back to `Backend/data/` as a test database. Run `git diff --check` before review.

### C. Independent review and repair

The reviewer must inspect the actual diff, live Debug app, DTO/API change, test changes, and screenshots against every binding decision. Blocking findings include: iOS restructuring; another LLM call; any selection/scoring change; an internal key/stage/expression in a default user layer; a modal auction/info-card path on macOS; missing visible selection; stale build/version mismatch; or use of production data for tests.

Write findings, including “no blocking finding”, to `archive/review报告/REVIEW_V2.4.1_20260813.md`. The builder repairs every confirmed P0/P1 finding, adds a regression test where practical, and repeats the full verification gate.

### D. Release-candidate preparation — stop before shipping

Only after the repaired full gate is green:

1. Run one release helper that sets `MARKETING_VERSION` in both `project.yml` locations to `2.4.1`, sets `CURRENT_PROJECT_VERSION` to `2`, updates `Backend/neckline/api/app.py::VERSION` to `v2.4.1`, runs `xcodegen generate`, and asserts the generated project has no version/build drift.
2. Run the full Backend and macOS test/build gate again; produce a local signed/unsigned Release archive only if existing local signing permits it.
3. Record artifact path, commit SHA, test results, and rollback point in the final review report or its short release addendum.
4. Stop. Do not run `sync_code.sh`, `sync_data.sh`, remote SSH, upload, notarization, or distribution.

Rollback before deployment is `git revert` of the v2.4.1 commit(s) and a rebuild of v2.4.0 Build 1. Because the backend contract is additive and has no schema migration, a server rollback leaves no data-reversal task.
