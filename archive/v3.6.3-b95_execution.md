## 2. 关键实现决定

### 2.1 执行事实与进度分离，恢复从未完成工作开始（P1-1）

现有`research_store`终态摘要已经绑定task、context、profile、revision和摘要hash。继续复用它和`k10_execution_item_checkpoints`，不另造调度框架/数据库表，也不改外部请求身份。

1. 冻结一次已理解/合并后的研究单元清单：单元身份、稳定顺序、事件派生载荷或现有检查点引用、输入hash。身份同时绑定原任务、精确资料revision、原配置/执行绑定与必要契约版本；不能用新的壁钟或attempt生成新身份。使用现有global/event检查点保存私有衍生物，原文/提示/回执不再复制到manifest。
2. 每片用必要字段批量投影查清单元状态，直接领取未完成/可继续的研究单元；已终态单元不再调用研究入口、逐条leaseguard或逐条触发snapshot回调。不能把`continue_research`、失败、unknown或仅存在snapshot当作终态缓存命中。原有“未知外呼阻止重发”的判据先于新请求准入。
3. snapshot事实已在task关联表里持久化；新snapshot及终态写入不再每次重写整份coverage。`researchSnapshotIds`、失败依赖、计数等消费者改从同一事实/必要投影读取；如原有报告/恢复消费者仍需coverage清单，仅在阶段转换/最终冻结物化一次。不能只加“ID已存在就return”，使新事件仍逐个写3.5MB树。
4. 允许“snapshot/终态已写、coverage或阶段登记未写”后崩溃；续跑须从事实表补齐，不重发相同wire。已有3.6.2任务缺新manifest时，只从其冻结输入及现有派生检查点分步建立本地索引；不重绑、不迁移旧业务、不默认恢复已终态失败任务。首轮构建manifest也要可跨片，不要求每片重建全部正文/标题派生物。
5. 私有执行进度只记录当前phase、已完成单元/组装计数、最后实际变化及片起止的进展差异；可区分真正推进、等待外呼/限流、只有续跑次数变化。没有实际变化不得刷新“最后进展”。该信号用于诊断，不新增任意次数/时长停止阈值，不把正常大任务或等待供应商直接置failed。

### 2.2 从研究到发布都可恢复，组装不再要求单片完成（P1-2）

采用局部、显式的阶段衍生检查点：`研究输入已冻结 → 研究单元推进 → 事件/公司组装 → 依赖排除已确定 → 全局排序 → draft已冻结 → 原子发布`。名称可按代码惯例调整，但每个阶段的输入、完成边界与恢复入口必须明确。

- **事件/公司组装**：拆出当前`run_discovery`第二遍循环；每个事件的verification、候选分类、背景/排除/待核/更新、issues及计数成为校验后的私有衍生结果。按稳定单元顺序读取未组装项，完成后写现有event检查点再推进游标；事件含大量公司时，必要的公司级组装也以同一event item下稳定分项key保存，避免单个大事件因重复前缀卡死。已完成项不会再次做metadata/classification或读取完整research round。
- **检查点结构**：完成衍生结果沿用`record_execution_checkpoint`不可覆盖约束；可变游标放小型task/阶段状态，不能在`status=pending`里塞未校验result，不能覆盖已完成行。断在“结果写完、游标未写”时由完成行推导前移，恰好一次计数，去重event/公司输出。
- **依赖排除**：在rank前根据全部输入的失败/未知及公司、来源依赖建立确定性结果；直接复用研究快照/单元投影，避免每片完整读所有snapshot树。失败单元影响同公司的现行排除规则保留，未知范围不能默认为安全。此阶段也要能检查点续进，不能把全量工作藏在一次不可恢复callback里。
- **全局排序**：只对完整汇总、已排除的候选集合做现有一次全局比较，不用分批排名代替全局语义、不先发前30家。冻结精确ranking输入hash/必要manifest；排序成功响应及其验证后的顺序持久化后才能冻结draft。崩溃发生在请求返回、响应落盘、排序衍生落盘或draft落盘之间，均须沿用原请求/回执复用，不再联网刷一遍。
- **最终物化/发布**：各事件输出按稳定顺序合并成现有DiscoveryRun/frozen draft，计数、相同公司多催化、D1/D2、来源版本与材料完整保留。阶段完成后下一片直接进入下一阶段，不回到研究入口。最终draft需要一次物化时必须验证实际规模下有界；若仍耗尽切片，继续拆分本地可恢复物化，不靠扩大110秒配置或删除budget guard过关。原有租约、晨报最终截止/closeout guard与外呼准入仍有效。
- 现有`_publish_scan → publish_opportunities → finish_task_with_publication`及outbox原子边界保持；任何私有中间结果不能提前变正式推荐。完成/partial可读结论以真实报告API、完整材料/引用和delivery为准。

### 2.3 缺父晨报的接口契约（P2-3）

仅使用晨报08:30已冻结的`b90MorningParent`，不借更旧晚报、不补入晚到父报告；新发现通道继续独立推进。

- `state=unavailable`表示无法冻结应复核的正式父报告，不能因targetCount=0记为完成。聚合coverage加入稳定gap **`morning_parent_unavailable`**；`reviewState`保留不可复核语义，晨报aggregate/report/status与delivery.outcome均为`partial`，`morningReview.state=unavailable`。
- delivery.gaps复用现有结构：`stage=morning_review`、`unitKind=report`、`unitId=当前晨报reportId`、`reasonCode=morning_parent_unavailable`、`companyScopeKnown=false`；无已知父引用时不造parent ID/公司/来源。文案为“昨晚正式报告不可用，无法复核原有推荐理由；本次新发现单独呈现”。聚合→delivery→v2_store刷新不能把这个gap覆盖掉；也不能因无review item被提前return丢失。
- 可读、完整且正式零推荐的父报告不是unavailable；复核目标0时允许复核complete，整体仍由真实来源/发现等缺口决定。失败、处理中、无父报告分别覆盖；partial但可读父报告沿用实际冻结目标及已有覆盖语义，不凭空补目标。
- 不新增公开Schema或报表类型。Swift对新reasonCode显示明确文案，延续已有partial/未知UI，材料不冒充推荐；主会话负责App实现及真实后端DTO解码/原生验证。Backend交付从隔离真实CLI/worker/API生成的“缺父partial”与“完整零推荐父”响应及对应原件API，不能手写替代fixture。

### 2.4 晨晚报告共用已消费事实（P2-4）

`freeze_collected_input`汇总所有已正式发布、可读、completed/partial晨晚报中的明确terminalRefs，按(documentId,revision)去重。只消费真终态资料；partial报告中非终态部分、失败未发布、unknown/在途依赖不推进。现有unknown跨任务阻挡保持；新revision/真实新进展仍可进入。

修正消费集合与previously-present边界，不顺便重定义业务窗、bootstrap、采集水位或晨报父报告锚点。晨报仅有新发现通道实际判断的资料才能按现有终态条件消费，不能把复核背景回读一概当新发现已判。晚报从集合排除晨报已判同revision；晨报隔夜发现时间窗不扩大。已冻结任务输入不追溯改写；本轮不重跑旧报告来“补消费”。

### 2.5 进度GET只读取统计投影（P2-5）

`execution_progress_for_scan`及直接调用链只用SQL聚合/JSON标量或短列表投影：状态、阶段、计数、绑定、必要安全错误、下一次retry、必要Tavily ref身份。不得SELECT整份coverage、所有result_json、标题manifest全部refs或原文，只为了计数。Tavily摘录统计在数据库join/去重完成，避免大IN参数与完整工具结果。

保持现有API DTO字段、null/unknown/partial、失败去重及状态语义；先明确字段到事实表的映射再替换查询。序列化大JSON投影遵循项目进程内并发锁规则；读路径无DDL/写入、无供应商调用，不读取回执正文。新内部phase/进展字段若无公开消费需求，留在小型执行检查点，不扩张UI范围。

### 2.6 公平领取与晨报截止优先（P2-6）

保留当前晨报及其截止收口的优先级；非晨报任务以**本轮进入可领取队列的时间**排序：首次任务用created_at，已续跑/重试任务用现有retry_schedules.updated_at，并仍满足not_before_at；过期租约恢复用其已确认时间边界。相同时用created_at/task_id稳定排序。一个晚报续跑释放后排到已等待采集/行情/其他任务后面，不再凭旧created_at/固定晚报类别无限占首。

晨报优先受现有固定09:20截止/终态机制约束，不能让已过期晨报无限continuation；不新设“紧急阈值”、占比或最长晚报时限。`claim_task_by_id`只领父任务明确拥有的child，仍保留；多worker原子租约、暂停control、retirement、unknown恢复判据不变。测试覆盖maintenance慢于1秒continuation的真实worker场景，不能仅靠调整sleep碰巧让采集插入。
