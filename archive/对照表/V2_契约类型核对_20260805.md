## 一、方法论(为什么不能只读 `schemas.py`)

**两层风险,分开验证**:

1. **pydantic 强类型字段(非 `Any`)**——`ReportOut(**kwargs)` / `BasketDailyOut(**...)`
   在 `app.py::_shape_*` 里是**真实构造**(非仅类型注解摆设,`app.py` 全仓零
   `response_model=`,但函数返回类型注解会被 FastAPI 当隐式 `response_model`,且更关键的
   是构造过程本身走 pydantic `__init__` 校验)——服务端若真发出不符声明类型的值,构造期
   即抛 `ValidationError`(500,响亮失败,不会悄悄把错类型送上线)。故这一层**服务端类型
   声明本身就是雷打不动的事实**,核对退化为"读 `schemas.py` 字段类型 vs 读 `Models.swift`
   解码类型,逐个比对名字",风险低、核对快。
2. **`Dict[str, Any]` / `List[Dict[str, Any]]` 自由字段**——pydantic 对 `Any` **零校验**,
   服务端写进去什么 Python 类型,原样序列化上线,`schemas.py` 在这一层**不提供任何事实**。
   真正的事实源是**实际写入代码**:`selection/basket_card.py::to_card_json()` /
   `report/basket_daily.py::card_to_public_dict()` / `db.py` DDL(如 `engine_api_version
   INTEGER`)。客户端对这类字段有两种应对:**多数走 `NKJSON`**(动态识别类型,天然不会
   `typeMismatch`,零风险)——但**少数字段客户端选择了强类型 struct**(`fingerprint` →
   `BasketFingerprint`;`sentiment`/`sectors` → `SentimentSnapshot`/`SectorSnapshot`;这些
   是本表的核心排查对象,`engineApiVersion` 与 `sentiment` 两个真实坑都出在这一类)。

**验证工具链**:①「真实生产载荷」回归测试
(`DTODecodeTests.swift::testDecodeRealProductionReportFixtureFullShapeAndTypes`,7 篮
143400 字节原文,今晚固化,详见 `archive/对照表/V2_契约三方对拍_20260803.md` §七第5条历史);
②本次新增独立 decode 测试台(`main.swift` + 抽取的 `ReportResponse.swift` + 真实
`Models.swift` 编译成可执行文件),拿 REST 端点真实响应(`api_env` 全新空库调
`GET /report/latest`)喂真实解码链路,**修复前先复现炸,修复后再验证不炸**,不是先改代码
再补测试兜底猜测。

## 三、发现的问题与修复

### 3.1 `BasketFingerprint.engineApiVersion`(当晚早些时候已修,commit `0eddac7`,本表补登)

服务端实际写入类型 = `int`(`selection/basket_card.py::BasketCard.engine_api_version:
Optional[int]` → `to_card_json()` 原样塞进 `fingerprint` dict → `db.py` 三处
`engine_api_version INTEGER` DDL 佐证)。客户端曾按 `String?` 解码,`typeMismatch` 顺着
`BasketCard.init(from:)` 的 `fingerprint` 那一路抛穿,拖炸**整份** `ReportResponse`。
修法:`engineApiVersion` 改 `Int?`,容错双态解码(数字优先、字符串数字也认)。详见该 commit
message 与 `CLAUDE.md` 同名坑条,不在本文件重复贴 diff。

### 3.2 `ReportResponse.sentiment` 解码未接 `try?`,空对象拖炸整份报告(本次新查出,已修)

**根因**:`ReportOut.sentiment: Dict[str, Any]` 是**必填、非 Optional**字段(`Tier 2`,
零 pydantic 校验)。`app.py::_empty_report(reason)`——`GET /report/latest` 当日无报告 /
`GET /report?date=` 查无该日报告**两条主路径共用**的降级响应——传 `sentiment={}`(Python
空 dict)。pydantic 序列化空 dict 恒是 JSON `"sentiment": {}`(空对象),**不是** `null`。

客户端 `ReportResponse.init(from:)` 对 `sentiment` 用的是裸
`try c.decodeIfPresent(SentimentSnapshot.self, forKey: .sentiment)`——**没有接 `try?`**。
`SentimentSnapshot` 是合成 `Codable`,九个字段除 `prevLimitUpPremiumAvg` 外全部非
Optional。`decodeIfPresent` 只在**键缺失**或**值为 JSON `null`**时安全短路返回 `nil`;
键存在且值是**非 null 但形状不对**的 `{}` 时,它会照常尝试完整解码 `SentimentSnapshot`,
在第一个必填键 `trade_date` 上抛 `keyNotFound`,且这个异常**没有任何东西兜底**,直接
向上传播炸穿整个 `ReportResponse.init(from:)`。

**为什么容易被忽略**:同一个函数里紧邻三行之后的 `intel`/`sectorMoneyflow`/
`dataFreshness` 早就接了 `try?`,注释原话明确写着"服务端恒是对象……空对象缺我方强类型
要求的字段,标准合成解码会直接抛错,这里用 `try?` 把'形状对不上'也当'没有'处理"——
`sentiment` 满足**完全相同**的前提,却是这一组四个字段里唯一漏掉 `try?` 的。手写测试
fixture 全部惯用 `"sentiction": null` 占位(该形状确实安全,但**从未在生产真实出现过**),
所以这个坑在既有测试矩阵下从未被触发。

**实测复现**(2026-08-05,`api_env` 全新零报告库,真打 `GET /api/v1/report/latest`):

```
"sentiment": {}          ← 实测原文,非 null,非缺键
```

拿这份真实响应喂独立 Swift 解码测试台(`main.swift` + 抽取的 `ReportResponse.swift` +
真实 `Models.swift`):

```
修复前:DECODE FAILED — DecodingError.keyNotFound: Key 'trade_date' not found ...
       Path: sentiment
修复后:DECODE OK
```

**修法**(`client/Neckline/Networking/APIClient.swift`):
`sentiment = try c.decodeIfPresent(...)` → `sentiment = try? c.decodeIfPresent(...)`,
与 `intel`/`sectorMoneyflow`/`dataFreshness` 同一模板,**逐字节最小改动**(仅加一个
`?`)。**触发路径不是边角情形**——全新安装、非交易日盘前、任何"当天/该日无报告"的历史
回放查询,统统会走 `_empty_report()`,与 `engineApiVersion` 同一种"整份报告解不出、今日
计划页退回空态"的失败模式,只是触发条件从"有篮子的报告"换成了"没有报告"。

**回归测试**:`DTODecodeTests.swift::testDecodeEmptyReportRealShapeSentimentIsEmptyObjectNotNull`
固化 2026-08-05 真实 `/report/latest` 空库响应原文;顺带订正
`testDecodeReportDegradedEmpty` 此前手写 `"sentiment": null` 的错误假设,改成真实的 `{}`。

## 四、核查后判定安全、不改动的记录

### 4.1 `DataFreshness` 的合成 `Codable` 安全性依赖一条隐性写侧不变量

`DataFreshness` 有两个非 Optional 字段(`sectorLagDays: Int`、`stale: Bool`,来自
v1.4-①-C 最早那版形状),其余六个(`industryStrengthDate/LagDays/Stale`、
`scanLayerDate/LagDays/Stale`)均为 Optional。若服务端字典**恰好**只缺
`sectorLagDays`/`stale` 而其余字段仍在,合成解码会因这两个必填键失败,进而(在外层
`try?` 保护下)把**整个** `dataFreshness` 判定为 `nil`,连带丢弃本该有效的
`industryStrength*`/`scanLayer*` 信息——但这个"部分损坏"的写法**在当前代码库里不存在**:
`pipeline.py::build_report` 里 `data_freshness = {**sector_freshness.to_public_dict(),
**industry_freshness.to_public_dict(), **(scan_freshness... or {})}`,
`sector_freshness.to_public_dict()` 恒**无条件**摊开(`SectorDataFreshness` dataclass
`sector_data_date`/`lag_days`/`stale` 三字段永远同时存在,`compute_sector_freshness` 的
四个返回分支无一遗漏任何一个),故 `sectorDataDate`/`sectorLagDays`/`stale` 三键要么**一起
出现**,要么整个字典是 `{}`(建于 v1.4-①-C 之前的老报告,或 `_empty_report()` 降级态)。
两种情况都被现有代码正确处理:全空 → 靠外层 `try?` 归一成 `nil`(=「该版本还没有新鲜度
概念」,与产品语义相符);三键俱全 → 正常解码。**判定:安全,不改**——但已订正
`Models.swift` 里一处原本写着"因为 dataFreshness 属于每次响应重新构造那一类"的**不准确
注释**(它其实和 `reviews.result_json` 一样是写入当时冻住的历史快照列,只是恰好两个必填
键的写侧不变量成立而已);新注释同时点名这正是 `sentiment` 那个坑的反面教材,提醒未来
维护者新增本类型的非 Optional 字段前,先确认写侧真的会让新字段与
`sectorLagDays`/`stale` 恒同现,否则必须连同调用点一起手写容错。

### 4.2 `NKJSON` 透传字段的 NaN/Infinity 已知风险类别(未发现具体实例,记录风险面)

`tierBreakdown`/`verificationSpec`/`invalidationSpec`/`mech`(成员机械面板)等自由结构
字段全部走 `NKJSON`,对**类型误判**(本表核心关注点)天然免疫。但 `NKJSON`/Swift
`JSONDecoder` 与 Python `json.dumps()` 共享同一个已知的**正交**风险类别:Python
`float('inf')`/`nan` 经 `json.dumps()`(默认 `allow_nan=True`)会产出 `Infinity`/`NaN`
这类**非标准 JSON 字面量**,标准 `JSONDecoder` 解不出(与本表主题"名对型不对"不同,这是
"值本身不是合法 JSON"的独立故障模式)。项目里已有一处主动防线
(`review/reconcile.py::_finite()`,专门把 `profit_factor`/`profit_loss_ratio` 的 `inf`
转 `None`)。本次核对未在篮子契约的浮点产出路径(`mech_score`/`industry_lift`/
`rs_rank` 等)发现具体的 NaN/Inf 泄漏实例,**不升级为待办**,仅记录风险类别供未来排查
"某个字段偶发解码失败"时参考。
